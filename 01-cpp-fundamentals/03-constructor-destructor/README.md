# 实验记录：01-cpp-fundamentals/03-constructor-destructor

## 1. 学习目标

- 理解构造函数建立对象可用状态、析构函数释放所拥有资源的职责。
- 理解 RAII 如何在正常返回和提前返回时避免遗漏资源清理。

## 2. 前置知识

- 局部自动对象的生命周期。
- `std::string`、成员初始化列表和基本函数返回值。

## 3. 实验要求

- 实现只打印资源获取与释放日志的 `MockFile`，不调用真实系统 `open()`。
- 在 `processFile()` 中创建局部 `MockFile`，分别覆盖提前失败返回和正常成功返回。
- 在 `main()` 中输出两次调用结果，观察析构日志是否先于调用结果出现。

## 4. 我的实现思路

- 用构造函数输出 `open`、析构函数输出 `close` 来模拟资源成对管理。
- 用 `has_error` 触发提前返回，观察局部对象仍会在函数返回前析构。

## 5. 编译和运行

- 编译：`g++ -std=c++17 -Wall -Wextra -Wpedantic -Werror -g main.cpp -o constructor_destructor`
- 运行：`./constructor_destructor`

## 6. 测试与预期结果

- 2026-10-14 实际验证：严格警告编译通过并运行成功。
- `processFile(true)` 输出 `Failed`、`close: /dev/mock0`、`failed result: false`，证明提前返回前发生析构。
- `processFile(false)` 输出 `Succeed`、`close: /dev/mock0`、`succeeded result: true`，证明正常返回前同样发生析构。

## 7. 遇到的问题

- 学员明确请求后，辅助修正了上述语义并在关键处补充了说明注释；未引入真实文件操作或额外抽象。
- 初始不了解 RAII 术语；已结合 `MockFile` 的构造/析构日志说明其含义。

## 8. 知识总结

- RAII（Resource Acquisition Is Initialization）把资源建立放入构造函数，把资源释放放入析构函数。
- 局部对象构造成功后，无论函数正常返回还是提前 `return`，离开作用域时都会确定性执行析构函数。
- C 风格代码必须在每条返回路径手动配对 `close(fd)`；Java 的 GC 时机不确定，外部资源仍应使用 `try-with-resources` 或显式关闭。

## 当日学习记录：2026-10-14

### 知识概要

- 通过模拟文件资源，学习构造函数建立资源状态、析构函数归还资源的 RAII 模式。
- 验证 `return false` 不会跳过局部对象析构。

### 必须掌握的重点

- 构造成功的局部对象在离开作用域时会确定性析构。
- 析构函数可集中实现资源清理，避免 C 风格多分支手动 `close()` 的遗漏。
- Java GC 不能保证外部资源的确定释放时刻。

### 实践与验证结果

- 学员独立完成 `MockFile` 初版，已正确观察到两条路径均输出 `close`。
- 学员请求后，辅助修正失败/成功分支语义并增加返回结果输出；严格编译和运行验证均通过。

### 原理考核记录

- 问题：为什么正常返回和提前 `return false` 都不需要手写 `close`？
- 学员原始回答摘要：析构函数负责 `close`；对象生命周期结束时会自动调用析构函数，从而触发关闭。
- 纠正与结论：补充 RAII 名称和含义；构造函数建立资源，析构函数在作用域退出时确定性清理。
- 问题：为什么 Java GC 不能替代确定时刻的资源释放？
- 学员原始回答摘要：GC 调用时机不确定，需要手动处理资源释放。
- 纠正与结论：补充 Java 通常使用 `try-with-resources` 或显式 `close()`，而不是依赖或手动触发 GC。
